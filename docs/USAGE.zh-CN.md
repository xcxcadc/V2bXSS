# 二开 V2bX：安装与节点安全审计使用说明

本仓库是 `xcxcadc/V2bXSS`，当前分支为 `dev_new`。安装入口见
[仓库首页](../README.md#软件安装)。它构建本仓库源码，不下载上游 V2bX 发行版。
已有原版节点使用独立原位升级命令（保留原服务与配置）：

```sh
wget -N https://raw.githubusercontent.com/xcxcadc/V2bXSS/dev_new/upgrade-legacy-node.sh && bash upgrade-legacy-node.sh
```

新服务器或独立测试服务使用下面的菜单，两条入口互不调用、服务及备份路径独立。
在 Linux root / systemd 环境运行下面一条命令，按中文菜单选择安装：

```sh
wget -N https://raw.githubusercontent.com/xcxcadc/V2bXSS/dev_new/install.sh && bash install.sh
```

安装器自动准备依赖和满足版本要求的独立 Go 工具链，校验官方工具链 SHA256 和
Go 模块后构建二开。首次需要数分钟；不要求手动 clone、取提交号或预装 Go。
首次运行和安装结束均显示管理菜单；以后输入 `v2bx`（或 `v2bxss`）重新打开。
选择 2 更新，配置、证书和混淆完整保留。绿色编号逐行显示，协议/内核/证书分步选择。

## 安装后怎样使用

1. 使用适配了本功能的面板，在“节点安全审计”中管理规则、查看命中证据和节点状态。
   本菜单独立于内鬼风控工作台。仅安装节点程序不会给旧面板自动创建菜单。
2. 首次选 1 后，按配置向导填写自己的面板地址、节点 API 密钥、节点类型/ID、证书。
   可以连续添加多个节点，也可以导入已有标准 JSON。复杂配置参考
   [HY2 配置示例](../example/security-audit-hy2-test.json)。配置凭证只留在服务器。
3. 菜单安装会自动备份、安装并启动独立的 `v2bxss.service`，开启开机自启。
   菜单 11 追加节点；菜单 3 编辑/导入/修正配置，先备份再重启；菜单 7/8 看状态和最近日志，
   菜单 8 持续查看实时运行/连接日志，按 Ctrl+C 退出管理菜单，不停止节点服务。
   主菜单和操作后的等待输入处同样可用 Ctrl+C 退出；运行状态和开机自启显示中文。
   原有 `V2bX` 服务独立管理；请避免对接相同端口。高级参数方式仍默认只打印计划。
   新版目录统一为 `/etc/v2bxss`；管理命令缺失时运行 `bash install.sh repair`。
   原版 `/etc/V2bX` 或旧独立目录使用菜单 12，经确认后迁移。
4. 在后台新增规则，先选择指定测试节点、观察模式；查看“节点状态”的请求版本和
   已应用版本一致，再测试命中。旧面板缺少审计 API 时，节点原业务继续运行。

配置输入有误会就地重填。应用后启动失败，保留新配置并打开修正菜单，可编辑、重试、
查看日志或确认恢复旧配置；退出不会抹掉输入，可经菜单 **3 → 3** 继续。
草稿与修改前备份保留在 `/etc/v2bxss/manager/drafts/`，文件权限 0600，不上传仓库。
保留错误运行配置期间节点可能不可用；程序版本升级的失败回滚仍然有效。
某节点暂时没有授权用户时，节点保持监听和轮询，拒绝未授权连接，不阻止其他节点启动；
面板之后下发符合条件的用户会自动生效，不必重启。配置或证书等真正的启动错误仍会
返回非零退出码，由服务管理器按现有策略处理，具体错误可在菜单 8 查看。
`v2bx` 优先使用 `/usr/local/bin/v2bx` 的二开入口，上游 `/usr/bin` 文件不覆盖；
若缓存旧路径先运行 `hash -r`。已有不相关的同名 local 命令则保留，使用 `v2bxss`。

节点沿用原有节点认证，自动访问以下接口；不需要另填审计账号或逐节点复制后台规则：

```text
GET  /api/v1/server/UniProxy/securityAudit/config
POST /api/v1/server/UniProxy/securityAudit/events
```

`observe` 记录命中，`block` 拒绝命中的目标连接。两者都不修改账号封禁、订阅、
套餐或流量余额。只记录已认证用户命中规则的必要连接元数据，不记录未命中的完整浏览史。

## 实时运行 / 连接日志

安装了本次更新的管理器后：

```sh
v2bxss logs -f
v2bxss logs --follow --lines 200
# 查看原版原位升级后仍沿用的服务；不会接管或重启它
v2bxss logs -f --service V2bX.service
```

`logs` 不加 `-f` 时显示最近 100 行后退出；`--lines 0` 只等待新日志，最大 10000。
时间使用服务器时区的完整日期。Ctrl+C 只结束查看，不停止节点。不需要为新增查看命令
更新节点二进制、配置或重启服务。

旧管理器尚未更新或原版原位升级未安装 `v2bxss` 快捷入口时，可直接使用：

```sh
journalctl -u v2bxss.service -f -n 100 --no-pager -o short-iso
# 原版原位升级的服务对应以下命令
journalctl -u V2bX.service -f -n 100 --no-pager -o short-iso
```

这是 systemd 日志跟随，不是“所有用户全部访问记录”。是否出现连接记录取决于当前
内核日志级别和输出位置：原生 HY2 在 info 记录连接/断开，目标请求明细在 debug；
sing 使用其 `Log.Level`/`Output`；Xray 使用其访问/错误日志设置。若日志输出到文件，
应对已配置的日志文件使用 `tail -F`。查看器不自动开启 debug、修改输出或重启节点。
后台审计只记录规则命中，证据在“节点安全审计”页面查询，不保证每条都打印到 journal。

各协议的内核选择、规则边界与验证状态见[协议支持核对](PROTOCOL-SUPPORT.zh-CN.md)。

## 后台修改规则，需要重启节点吗

**不需要重启所有节点。后台托管规则默认每 30 秒自动拉取，替换整份策略。**
命中证据默认每 5 秒批量上报；网络故障或上报重试会延长可见时间。

| 操作 | 是否需要重启 | 怎样确认 |
| --- | --- | --- |
| 后台新增、修改、启停、删除托管审计规则 | 不需要 | 等待节点“已应用版本”等于请求版本，正常约一个 30 秒轮询周期 |
| 更改规则适用节点 | 不需要 | 分别检查移出、移入节点的已应用版本 |
| 首次安装或升级二开二进制 | 需要重启被升级的服务一次 | 查看服务 PID、版本、节点回执；不是重启服务器或所有节点 |
| 修改节点 API、监听、证书、`RuleListPath`/执行开关等配置 | 需要重载该配置对应实例 | 配置监视器可能自动重建；独立安装示例关闭监视，需重启该服务 |
| 修改已配置的本地 RuleList 文件内容 | 不需要 | 在原节点配置拉取周期检查文件，即使 HTTP 304 也检查；看本地规则哈希、时间及错误 |
| 修改面板原“路由管理”规则 | 沿用原节点配置拉取机制 | 与新审计 30 秒周期不同；依节点配置更新及原内核路由机制而定 |
| 到期、流量用尽、移除节点用户 | 沿用用户资格同步 | 与目标规则独立，取决于原面板用户拉取周期，不能当作 30 秒审计同步 |

审计针对新连接。更改目标规则不会追溯切断已经建立的 TCP 长连接；原生 HY2 会复查
UDP 目标变化及策略版本变化后的数据包。若新规则未命中，先检查节点范围、启用状态、
版本和内核能力，不能只凭“点击保存成功”判断生效。

接口故障或新策略无效时保留最近有效策略，不清空现有有效规则。
显式停用规则/策略才是正常解除方式；直接停掉面板不代表节点规则已解除。

## 原生审计、默认规则与新增审计的区别

没有把上游安装器的外部文件或原始名单静默改成全节点启用的规则。
不同来源在后台分别展示：

| 来源 | 执行与管理方式 |
| --- | --- |
| 新增后台托管规则 | 在节点安全审计菜单新增、批量导入、启停、删除；由本二开热同步，可产生命中证据 |
| 原面板路由 `routes` | 原处理路径保留；“现有规则预览”和节点原路由清单只读展示，实际修改仍到原路由管理 |
| 节点本地 `RuleListPath` | 本二开新增显式文件读取；默认只预览，须设置 `RuleListEnforce: true` 才执行；后台展示文件回执，不改写远端文件 |
| Xray/sing 原始静态路由、外部 HY2 ACL | 保留原配置；不等同于上述 RuleList 或托管规则，不在本菜单自动接管 |

核对的上游版本中，`RuleListPath` 只有配置字段，未实现文件读取。因此不能仅凭填过
这个字段就认定原生文件审计已经运行。本二开增加读取、完整校验、去重和最后有效版本
保留；未配置该路径的节点保持原行为。

本地文件示例（位于配置中单个节点的 `ApiConfig` 内）：

```json
{
  "RuleListPath": "/etc/v2bxss/local-rules.txt",
  "RuleListEnforce": false
}
```

文件每行一个 Go RE2 正则，空行与整行 `#` 注释跳过。例如：

```text
# 仅示范匹配逻辑，不是已启用默认规则
(^|\.)malware\.example$
```

后台区分“配置了文件”“请求执行”“内核支持”“实际启用”，显示最后有效哈希、检查/
加载时间和安全错误码；不上传本机文件路径。文件无效时保留最近有效规则，错误在回执
中可见。本地原生阻断不产生新增托管审计事件，不能把其回执当作命中日志。
后台删除托管副本不会删除原路由或服务器本地文件。要从后台统一管理某条本地规则，
先转成合适的托管类型并验证，再从本地原文件删除旧项，避免双重阻断。

## 批量填写、导入与子域匹配

“匹配内容”可以换行；多行转到批量预览。支持 TXT 一行一条、JSON 字符串数组，
先预览转换、错误和去重，再确认导入。批量导入仅创建停用规则或观察规则，
不会把混合名单一次性变成启用的全局阻断；需要阻断的项在复核后单独修改。

```text
# 前缀可混用；不填前缀时使用界面选择的默认匹配类型
domain:malware.example
full:exact.example
regexp:(^|\.)malware\.example$
ip:203.0.113.0/24
port:25
protocol:bittorrent
```

| 类型 | 例子及边界 |
| --- | --- |
| 域名及子域 `domain_suffix` / `domain:` | `example.invalid` 同时匹配主域和 `api.example.invalid`，不匹配 `notexample.invalid` |
| 精确域名 `domain_exact` / `full:` | `example.invalid` 只匹配该完整域名；需要子域请选上一种类型 |
| 域名正则 `domain_regex` / `regexp:` | 使用兼容子集，不能直接粘贴任意 PCRE/XrayR 路由 JSON |
| IP/CIDR `ip_cidr` / `ip:` | 匹配请求的字面目标 IP，不另做 DNS 解析来推断命中 |
| 端口 `port` / `port:` | 支持单端口或闭区间，如 `25`、`6881-6889` |
| 应用协议 `protocol` / `protocol:` | `http/tls/quic/bittorrent/stun/ssh`；依赖内核识别能力，不能把 TCP/UDP 当作应用协议 |

URL 只在预览中取 hostname，不保存路径或查询参数。所有类型都不按逗号随意拆分。
预览去重不等于重新启用了数据库已有的停用项；请检查每条规则状态和适用节点。

## 最初外部清单的整理范围

提供了可复核的[普通网络管理规则示例](../example/security-audit-network-management.txt)：
矿池域名转为域名及子域匹配，SMTP 为目标端口 25，BitTorrent 为识别协议。
示例文件本身不会自动启用；应导入指定测试节点，按实际网络管理需要确认。
SMTP 端口阻断会影响正常邮件直投，矿池名单也不能覆盖所有挖矿行为。

原混合清单未整体部署：其中有重复、隐藏字符、注释混入表达式和带空分支的正则，
直接使用可能误匹配大量正常连接。按政治、宗教或新闻访问识别、跟踪、处罚用户的
条目未转换为可部署规则。其余普通站点也不能仅凭出现在旧名单里就认定有害。

## 内核支持与验证边界

| 内核 | 域名、字面 IP、端口 | 应用协议 |
| --- | --- | --- |
| Xray | 请求域名或已有嗅探结果；支持 IP/端口 | 依赖实际嗅探结果 |
| sing-box | 请求域名或已有嗅探结果；支持 IP/端口 | 依赖实际嗅探结果 |
| 原生 Hysteria 2 | 请求中的域名；支持 IP/端口 | 此回调不支持，不能声称 BitTorrent 协议规则已执行 |

本功能不会自动开启嗅探。直接访问 IP、ECH 或未得到域名时，域名匹配有可见性限制。
原面板路由的 HY2 支持不能由新增审计回调的能力倒推；请以实际执行路径和回执为准。
